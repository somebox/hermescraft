## (c) Architecture-falsification — the narrow-vs-wide comparison chain

- **Live pinch test (single trial, headline later falsified)** — `reports/agent-arch/2026-06-06-live-pinch-test.md` (2026-06-06, narrow card `pilot-navigator` to `:muster_south:`, wide card `flint`). *Tried:* same bot (flint on :3002), same model (`deepseek/deepseek-v4-flash`), same start `(33.5,69,-49.5)` → `:muster_south:` `(31,64,-29)`, single trial each side. *Worked:* narrow solved it in 5 API calls / 52 s / 265 k tokens-in, ending 1.6 blocks from target with clean §7 handoff metadata. *Failed:* wide blocked via `AUTO_STUCK_BLOCK` — bot descended into a 4-walls pocket at `(33,66,-50)`, the bot error literally told the worker to call `mc dig`/`mc escape` but the worker never reached the escape verb; the report's headline ("narrow bundle worked on a real task the wide bundle blocked on") was later disproven by replication. *Decided:* treat as a strong signal, not proof; replicate ×3 each side and try a different start without the trap geometry. (Report carries an inline update banner stating the headline did not replicate.)

- **Replication ×3 reverses the headline** — `reports/agent-arch/2026-06-06-pinch-test-replication.md` (2026-06-06, narrow `narrow1/2/3`, wide `wide1/2/3`; start `:muster_south:` → new mark `:pinch_target:` `(45,64,-43)`, ~20 blocks open surface, no trap). *Tried:* ×3 each side on a fair task. *Worked:* both sides 3/3 success; wide beat narrow on every metric except success rate — API calls 9 vs 11 (wide −18%), tokens-in 525 k vs 565 k (wide −7%), tokens-out 1,905 vs 3,337 (wide −43%), turn-1 in-context 38,833 vs 49,727 (wide −22%), wall time 65 s vs 100 s (wide −35%). *Failed:* the original "narrow wins" claim was wrong on single-phase nav — the trap geometry, not the skill bundle, was the variable; the "wide didn't reach `mc escape`" claim was also wrong (tool-call inspection showed wide did call `mc escape`, `mc goto_near`, `mc reachable`, 17× `mc terrain_top` — `mc escape` returned `ESCAPE_PILLAR error` so the fingerprint stayed identical and auto-stuck fired). *Decided:* the architecture's `target.md` prediction (narrow wins on context tokens / turn count / time) is NOT supported on single-phase nav; the next test must be multi-phase (the load-bearing claim) and must isolate SOUL-vs-skills. (Report carries a later banner: this replication is itself superseded by the clean comparison because both sides carried MEMORY.md contamination.)

- **Multi-phase chain vs one-card flint (test-invalidating contamination)** — `reports/agent-arch/2026-06-06-multi-phase-chain-comparison.md` (2026-06-06, chain cards `t_8c271b66`/`t_bc164665`/`t_3041ddf9`, one-card `t_0480cf78`; start `:island_start:` `(-29,64,-28)`, target `:island_tree:` `(-31,64,-26)` ~3 blocks). *Tried:* narrow chain navigator→miner→navigator vs wide one-card flint on "nav to tree, extract 4 oak_log, return." *Worked:* chain completed (61 calls / 3.47 M tokens-in / 726 s); card 1 clean (8 calls/96 s); card 3 returned (12 calls/4:48). *Failed:* **the comparison is invalid** — the flint card body specified the completion predicate "≥4 oak_log AND within 2 blocks of `:island_start:`" and BOTH conditions were already true at turn 0 because the operator had tossed 4 oak_log to clear inventory and the bot auto-picked them up while standing on the start mark; flint correctly read `mc status`/`mc read_chat`/`mc marks`, noted "task conditions already met," and the auto-stuck-check then fired on the no-state-change fingerprint — this was NOT a failure to mine, it was correctly identifying no work was needed. The 4-oak_log in flint's final inventory is the auto-pickup artifact, not evidence of mining. Chain card 2 also scope-drifted (crafted `oak_planks`/`sticks`/`wooden_axe` despite `agent-miner.md` §2 saying "No crafting"); the chain navigator died once in water on card 1 (hidden inside the 96 s); the flint body was ~12× longer prose than the chain cards. *Decided:* do NOT cite this report as evidence the chain pattern beats one-card; the architecture's narrow-bundle bet is untested on multi-phase work.

- **Experiment integrity audit (the contamination catalog)** — `reports/agent-arch/2026-06-06-experiment-integrity-audit.md` (2026-06-06 late evening, post-replication/post-chain). *Tried:* audit whether the pilot profiles had leftover state and whether test conditions exercised what the reports claim. *Worked:* identified what was actually fair — same model both sides, same bot/port 3002, same start position reset via direct HTTP `mc move` (no LLM cost), same `toolsets: hermes-cli`, marks via bot HTTP identical for both sides, Hermes v0.16.0 throughout. *Failed:* catalogued 12 contamination sources — (1) both pilot profiles auto-injected every prior run's summary at session start via `memories/MEMORY.md` (High, all narrow runs); (2) pilot-navigator's MEMORY had mock-world marks `mine_nw 20,60,20` / `base_anchor 0,64,0` / `ore_seam` from Phase 2/3 prototype (Medium); (3) pilot-miner's MEMORY had a successful `mc collect stone 4` from the Phase 3 mock test that taught it `mc collect <name> <count>` works in one call — the chain miner's first live action was `mc collect oak_log 4`, directly transferring this (Medium); (4) flint's MEMORY had every prior pinch-target nav cached (Medium, biased wide in replication); (5) flint's `profile.yaml` description "Miner. Deep ops, stone and ore extraction. L4 specialist." is a role-bias hint (Low-medium); (6) flint's `USER.md` working dir is `/Users/foz/src/hermes-webui` (Low, irrelevant); (7) flint's `.skills_prompt_snapshot.json` is **62 kB / 105 skills** vs pilot's **2 kB / 4 skills** — ~10 k tokens of irrelevant catalog noise (apple-notes, imessage, ascii-video…) at turn 1 (High); (8) flint's `SOUL.md` is **103 lines / 11.5 kB** of fleet-ops doctrine vs pilot's **17 lines / 743 bytes** auto-generated by `setup.sh` (High); (9) the chain miner crafted a crafting table + oak_planks/sticks/wooden_axe despite `agent-miner.md` §2 "No crafting" (Medium); (10) auto-marks from chain crafting (`craft_table_-31_64_-26`) polluted subsequent runs (Low); (11) **the flint one-card body literally specified the completion predicate and both conditions were already true at turn 0** — **test-invalidating** for the chain-vs-one-card comparison; (12) — *Decided:* the chain-vs-one-card comparison is invalid; the single-phase replication is mostly valid but needs caveats (the turn-1 context gap conflates catalog-noise favoring narrow with eager-preload favoring wide — inseparable from existing data); the architecture's bet hasn't been tested cleanly — the right test needs a no-MEMORY narrow profile with no eager preload and a wide profile stripped to mc-relevant skills, on a task whose completion predicate can't be pre-satisfied, ×5+ each side. The audit also concluded the narrow architecture's real lever may be `.skills_prompt_snapshot.json` size (60 kB catalog noise is a measurable cost), and that `MEMORY.md` is doing more architectural work than `target.md` accounted for — the worker is fresh per card but the profile carries learning across cards.

- **Clean ×3 comparison (reinstates the bet on cost metrics)** — `reports/agent-arch/2026-06-06-clean-comparison.md` (2026-06-06 late evening, narrow `n1/n2/n3` on `pilot-navigator`, wide `w1/w2/w3` on `flint`; start `:island_start:`, target `:island_tree:` ~3 blocks; reset automation in `prototypes/agent-arch/automation/`). *Tried:* ×3 each side with full reset between every run — `reset_profile.sh` truncates `MEMORY.md` to 0 + deletes `state.db` + clears `sessions/` + truncates `agent.log` + removes `.skills_prompt_snapshot.json` (Hermes regenerates); `reset_bot.py` tosses inventory + walks 12 blocks for despawn + returns to start; `verify_clean.sh` asserts the baseline. *Worked:* turn-1 context is now deterministic per profile — narrow runs landed at 49,137 / 49,139 / 49,137 tokens (2-token range); wide at 38,585 / 38,587 / 38,585 (2-token range), so all per-run variance is in-conversation drift not contamination. Headline on clean data: **narrow wins on cost** — API calls 8 vs 11 (wide +33%), tokens-in 428,398 vs 643,679 (wide +50%); **wide wins on wall time and output volume** — wall 74 s vs 65 s (wide −12%), tokens-out 3,041 vs 2,465 (wide −19%); both 3/3 success. *Failed:* the contaminated replication's "wide beats narrow on every metric" headline is reversed — contamination was helping wide (its MEMORY had directly-relevant prior pinch-target navs cached) and hurting narrow (its MEMORY had mock-world coords `mine_nw 20,60,20` / `base_anchor 0,64,0` that may have biased it toward nonexistent marks); on clean state narrow improved 24% tokens / 27% calls / 26% duration while wide got 23% worse tokens / 22% worse calls / unchanged duration. *Decided:* the architecture's `target.md` bet IS supported on the metrics that scale (cost and turns): three of five metrics favor narrow (total tokens −50%, turn count −33%, final-in-context ~−13%), one favors wide (wall time −12%), one tie (success 3/3). The 11 k-token turn-1 gap is the eager `skill_view` preload in the narrow SOUL vs flint's lazy load — narrow's per-call cost is higher but its total call count is lower. Caveats: n=3 (narrow ranged 51–111 s wall — need n=5+); trivial 3-block task (the bet is about multi-phase chains); different SOULs by design (17-line generated vs 103-line production — some "narrow wins" may be "minimal SOUL wins"); same model both sides (the architecture also predicts narrow should permit a cheaper model — untested).

- **Multi-phase clean plan (not yet executed)** — `reports/agent-arch/2026-06-06-multi-phase-clean-plan.md` (2026-06-06, status: plan). *Tried:* scope the next clean test — narrow 3-card chain (navigator→miner→navigator) vs wide one-card flint on "nav to `:island_tree:`, extract 4 oak_log, return to `:island_start:`," ×3 trials alternating (n1,w1,n2,w2,n3,w3), reset once per trial not per phase (MEMORY may grow within a chain trial — intended architecture behavior). *Worked:* the wide one-card completion predicate is fixed to use **inventory delta** (`oak_log_count ≥ start_oak_log_count + 4`) not absolute count, and reset clears the bot to 0 oak_log before each trial, so the bot MUST mine to complete — this is the explicit fix for the contamination that invalidated the previous chain attempt. *Failed:* not yet run. *Decided:* decision matrix framed as information-not-setback — (A) if narrow wins by ≥ same margin as single-nav (≥33% calls, ≥50% tokens), the scope-reset claim holds on multi-phase, scale; (B) if narrow wins by less, per-card scope reset is helpful but not dominant, the strategic case (parallelism/review/evolution) does more of the work; (C) if narrow loses to wide on cost, splitting into 3 cards costs more than 1, the narrow-bundle bet doesn't pay per-task and the strategic case must justify the architecture alone. The plan explicitly states this test cannot prove the architecture is the right call — its only job is to validate the new model doesn't make per-task work worse and surface the levers on context size and scope; the strategic bet (parallelism, review, evolving tools, planner, self-improvement loops) is not measured by any per-task token comparison.
