Hermescraft Architecture

A visual guide. Six categories of thing, one shape language, one mental model: a robot factory with software-engineering on the inside, an episodic memory it all shares, and a back-office board where the team improves itself.
design exploration · 2026-06-05 · canonical: README + target.md · sync bot names: pip, mox, zee, bix, glim

1 · Vocabulary

Six categories. Each has a color, a shape, and a job. Everywhere a thing appears in this guide it uses its own shape, so a glance tells you what kind of thing you're looking at.

Role
An architectural concern: planning, allocation, execution, review. Abstract.
Bot
A Minecraft body. Mineflayer process + registry entry (data/bots/<bot>.yaml). pip, mox, zee.
Agent
A Hermes profile holding expertise (SOUL + skills + memory). Names start with @. @miner, @navigator.
Workspace
Storage for state and code. Shared tree data/workspace/ + agent Hermes homes. Git-backed.
Card
A kanban task. assignee=<agent> + optional metadata.bot=<bot> for bot-bound work.
Human
The operator. Sets goals, reviews, intervenes on edge cases. Not the orchestrator.

3 · Concerns and who fulfills them

Architectural roles are concerns — abstract jobs that must be done. Each concern is fulfilled by one or more agents. The role is the contract; the agent is the implementation. (There is no "Steward" bot in this model — the planning concern is fulfilled by @planner, who is bot-less.)

4 · A card's shape

A card pairs an agent (who/what kind of work) with a bot (which body) when both are needed. Logically these are two fields. In Hermes' native schema, agent compiles to the skills array and bot compiles to assignee.

1 · Operator wrote (free-form)
title: Stock base with iron status: triage body: @navigator to :mine_nw: @miner 16 iron + 8 coal @navigator return to :base: @crafter smelt + deposit
Mention DSL. No bot named. @planner parses + validates marks.
2 · After @dispatcher bound it
id: t_b3 (child 2 of 5) title: Mine 16 iron + 8 coal status: ready assignee: miner # Hermes profile metadata.bot: pip # body to drive skills: [agent-miner, minecraft-mining] parents: [t_b2] max_runtime: 1800s idempotency: mission-X-2
Concrete card. @dispatcher picked pip via affinity (just arrived at mine).
3 · After worker completed
id: t_b3 status: done result: PASS metadata: inv_delta: {iron:+16, coal:+8} exit_pos: [276, 64, 78] marks_updated: [mine_nw_d3] duration_s: 1342
Handoff metadata. Next phase (@navigator return) reads exit_pos as start.
How spawn composes them
Hermes' kanban dispatcher loads ~/.hermes/profiles/miner/ (the agent's home: SOUL, model, skills, memory). Our spawn layer reads metadata.bot, looks up data/bots/pip.yaml, and injects MC_API_URL + MC_USERNAME at worker spawn. The agent profile's config.yaml declares env_passthrough: [MC_API_URL, MC_USERNAME] to accept them. Agent expertise + injected bot body = the worker.

7 · Many cards have no bot

Specialist agents do plenty of work that needs no Minecraft body: planning, allocation, judgment, watching, curating the recall stream, maintaining scripts. These cards run in parallel with bot work and don't compete for bot time. @planner, @dispatcher, @overseer, @reporter, @engineer are always bot-less. @crafter is sometimes bot-less (inventory audits, material budgets). @sentinel is usually bot-less but patrol variants bind a bot.

Bot-bound   @miner driving pip · mine 16 iron at :mine_nw:

Needs a body in the world.
  • Hermes profile: ~/.hermes/profiles/miner/ (the agent)
  • Spawn layer injects MC env from data/bots/pip.yaml
  • Holds per-bot mutex on metadata.bot=pip
  • Runs ~30 minutes
  • Heartbeats every 5-10 min
  • Writes inventory delta on complete; recall.resource(subject) and other presets (see data-api.md)

Bot-less   @crafter · material budget for road-bluff-v4

Pure data work — reads the shared workspace, writes a budget.
  • Hermes profile: ~/.hermes/profiles/crafter/ (the agent)
  • No metadata.bot → no MC env injected
  • No per-bot mutex (any number can run)
  • Runs ~30 seconds
  • Reads infra/ingest/plans/road-bluff-v4.json, production/generated/stockpiles.json, queries recall.near?subject=stone&type=resource
  • Writes budget back as a comment on the parent card

8 · Workspaces: layered access, shared brain, two boards

Workspaces hold state and code — plans, runbooks, skill bundles, scripts agents run to parse blueprints or score affinity. Three things make this work: a five-layer access model that hides the framework source from agents, a single domain-organized workspace that the whole team reads and writes (governed by OWNERS.yaml), and a back-office kanban board where script and plan changes flow through PR review.

8a · Five-layer access model

Agents see the workspace, their own Hermes home, and a curated set of distributed commands. The framework source tree is invisible at runtime.

1
Framework / system bot/ · plugins/ · scripts/ · dashboard/
Agent runtime access: none
Modified by humans + developers
2
Distributed commands bin/mc · bin/marks · bin/workspace
Agent runtime access: execute only
Installed to each profile's PATH at deploy
3
Profile content ~/.hermes/profiles/<agent>/{SOUL.md, skills/, config.yaml}
Agent runtime access: Hermes-managed
Deployed from data/workspace/reference/{skills,souls}/
4
Shared workspace data/workspace/{geo, infra, production, operations, reference}/
Agent runtime access: read freely; write per OWNERS.yaml
Tracked in git, per-world/scenario
5
Agent home ~/.hermes/profiles/<agent>/{memories/, sessions/, .env}
Agent runtime access: Hermes-mediated
Secrets never readable; memory via the memory tool

Workers spawn with cwd=data/workspace/; a pre_tool_call hook in the landfolk plugin enforces the allowlist on the file and terminal tools. Layers 1-3 are build-time / deploy-time. Layers 4-5 are runtime mutable.

8b · The shared workspace: five domains, each split into ingest vs generated

Organized by domain, not by agent — work is collaborative. Ownership lives in OWNERS.yaml. Each domain separates designed input (ingest/) from computed output (generated/) so PR diffs don't drown in compaction noise.

geo/
Places, worksites, routes, POIs
ingest: route + worksite templates
generated: worksites.json, routes, POIs, placemark-audit
scripts: classify-worksite, path-sim
infra/
Buildings, structures, blueprints
ingest: plans/ (road-bluff-v4.json, …)
generated: structures.json, construction-log.jsonl
scripts: parse-blueprint, verify-structure
production/
Resources, recipes, goals
ingest: recipes, budgets/, goals/<bot>.json
generated: stockpiles, deficits, goal-metrics
scripts: calc-materials, compose-budget
operations/
Fleet, dispatch, defense, runbooks, regions
ingest: regions/, runbooks/, post-mortems/, threats, loadouts
generated: dispatch-log, intent-log, epic-judgments
scripts: score-affinity, compose-fleet-state
reference/
Skills, SOULs, guides, research
ingest: skills/, souls/, guides/, research/
generated: project-log.jsonl
scripts: lookup-recipe

Skill bundles + SOULs live in reference/ingest/. The deploy script installs them into each profile's skills/ + SOUL.md. The framework keeps only the install machinery; the expertise is workspace content, versioned per world/scenario.

# data/workspace/OWNERS.yaml — the single-writer convention, made explicit # write: single canonical writer (for ingest/) # approve: PR-style approval before merge # compact: maintenance writer (for generated/) geo/ingest/route-templates.yaml: {write: navigator, approve: overseer} geo/generated/worksites.json: {compact: navigator} infra/ingest/plans/: {write: builder, approve: engineer} production/ingest/recipes.yaml: {write: crafter, approve: overseer} operations/ingest/runbooks/: {write: any, approve: overseer} reference/ingest/skills/**: {write: engineer, approve: operator} reference/ingest/souls/**: {write: engineer, approve: operator} **/scripts/**: {write: engineer, approve: overseer}

Skills, SOULs, world regions, and goal definitions use approve: operator because they shape agent behavior or world policy. Adding an agent: add their rows to OWNERS, no directory shuffling. Confused? grep <path> OWNERS.yaml tells you who writes there.

8c · Two boards: operations & back-office

A kanban board is a unit of cards + dispatch + workers. We run two. Different cadence, different reviewers, different metrics.

landfolk-ops   in-game work

Real-time (minutes). Per-bot mutex enforced.
Cards[NAV] [MINE] [BUILD] [CRAFT] [DEFENSE] [SUPERVISE] [MAINT] [URGENT] …
Workersexecution agents · @dispatcher · @planner · @overseer · @sentinel
Mutexyes — landfolk plugin on metadata.bot

landfolk-backoffice   the team improves itself

Async (hours-days). Workers run on git worktrees, parallel-safe.
Cards[BUG] [FEAT] [REFACTOR] [RESEARCH] [DOC] [MR] (merge request)
Workers@engineer (primary) · @overseer (reviews) · @planner (research)
Mutexnone — branch-per-card via Hermes -w worktrees

kanban_create --board <name> selects the board per card; profile configs declare which boards they participate in. The back-office board exists so code, plan, runbook, and skill changes flow through proper review — same agent-driven kanban flow, just a separate lane with PR mechanics.

8d · PR-via-card: how the team ships its own improvements

When @builder finds calc-materials.py crashes on tilted blueprints, the bug-fix moves through the back-office board on a git-worktree branch, with @overseer or operator review per OWNERS.

1 · Find
@builder hits crash
Files [BUG] card on landfolk-backoffice; original ops card blocks with tool_bug:calc-materials
2 · Claim
@engineer claims [BUG]
Spawns in a fresh worktree (.worktrees/hermes-<hash>/, branch hermes/fix-calc-materials)
3 · Code
@engineer edits
Modifies production/scripts/calc-materials.py, runs tests, commits
4 · MR
Files [MR] card
Assignee: @overseer (or operator per OWNERS); body: branch + diff + test output
5 · Review
@overseer / operator
Reviews diff. Approve → merge to main; reject → comments; @engineer revises
6 · Resume
Ops card unblocks
Next @crafter run uses the fixed script

Same flow works for blueprint revisions (infra/ingest/plans/), runbook updates (operations/ingest/runbooks/), skill bundles (reference/ingest/skills/) — anything OWNERS marks approve:. This is the factory metaphor in full: line workers do production on the ops board, engineers maintain the machines on the back-office board, QA reviews via PR. Every change is a card; every artifact change is a commit; every review is a human-readable diff.

9 · Recall stream: episodic memory the fleet shares

A host data API holds a single append-only stream — what an agent saw, where, when. The whole fleet writes into it; the whole fleet queries it. Recall is episodic memory. Marks are committed coordinates. Workspaces are audited content. The recall stream is the cheap intermediate that lets @farmer's glimpse of iron at (22, 98, 10) turn into @miner's next card body, with no spatial entity model on the write path.

1 · See
@farmer on zee spots iron during a scene scan

2 · Report

{ subject, type, where, who, card_id? }

3 · Persist
Host API stores the event (SQLite or JSONL+index) with dedupe window
4 · Plan
@planner reads a new [MINE] intent. Card body mentions iron.
→
5 · Recall
recall.near?subject=iron_ore&type=resource&…  
Top hits injected into the card body before dispatch
→
6 · Wake
@miner on pip wakes already knowing where to go

Each event has a subject (what it is about) and a type (closed enum: resource, blocked, damage, depleted, note). No free-form refs bag on the write path.

POST /api/workspace/recall/events { "subject": "iron_ore", # block / item / mob id "type": "resource", # resource | blocked | damage | depleted | note "qty": 1, "where": { "world": "world", "x": 22, "y": 98, "z": 10 }, "who": { "agent": "farmer", "bot": "zee" }, "card_id": "t_abc123" }

Live   Host data API

Append-only stream, high write rate, transactional reads, optional clustered hints.
  • POST /recall/events — append one sighting
  • GET /recall/near?subject=&type=&x=&… — task-time lookup
  • GET /recall/events?subject=&type=&since= — tail by subject/type
  • GET /recall/hints?subject=&type=&near= — derived clusters (optional)
  • Also hosts ops state: fleet-state, capacity-forecast, intent / dispatch / judgment logs

Compacted   Git workspace generated/

Low write rate, diff-reviewable, snapshot-stable. Compaction cards bridge stream → git.
  • [COMPACT] geo reads recall/events since watermark
  • Clusters recurring subject + type by location
  • Writes geo/generated/worksites.json, production/generated/stockpiles.json
  • Archives pre-watermark rows to archive/recall/<year-week>.jsonl.gz
  • @reporter is the named curator; folds into @overseer at MVP

What the recall stream is not: not a chest database (chest snapshots stay on bot HTTP), not a region authority (regions stay on bot for dig/place enforcement), not a replacement for marks (marks remain committed fleet agreement — compaction may produce marks, never replace them). The stream is episodic; marks are committed; workspaces are audited. Three layers, three cadences, one mental model.

11 · The hard parts, plainly

Conceptual gotchas worth holding in mind.

ConstraintLate binding is not native

Hermes v0.15 requires assignee at kanban_create. @dispatcher binds at write time, not at dispatch. WS event subscription handles bots that die between bind and dispatch via kanban reassign.

PrimitiveThe lease already exists

claim_lock at dispatch + kanban_heartbeat (every 5-10 min) + 4hr TTL + reclaim on PID death. The lease primitive is given; per-bot exclusion sits on top via the landfolk plugin.

Constraintmax_in_progress is global

v0.15's cap is board-wide, not per-assignee. Our per-bot mutex lives in the landfolk plugin's gate-check, not in Hermes core. Don't expect upstream features to retire it.

Tool fitDelegation is narrow

Synchronous, parent-bound, non-durable, max depth 3. Not a substitute for phase-as-card outer work. Useful only for intra-phase specialization inside short bot-less cards (e.g. @crafter material budgets).

DisciplineSkill bundles fence behavior

@crafter doesn't dig holes because mc dig isn't in its loaded catalog. Discipline is structural — the model can't reach for verbs it doesn't know about. Bundle quality is architecture quality.

DisciplineRoles are abstract; agents are real

"Planning" is a concern; @planner is the agent fulfilling it. You can swap implementations (rewrite @planner) without changing what the role means. Don't conflate them when reasoning about the system.

SequenceBuild observability first

Before binding logic, ship the dashboard lease panel + fleet-state file + recall stream skeleton. Validate that what you see matches reality. Only then add scoring, maintenance, preemption. Each step reversible; no big-bang.

DisciplineWorkspaces are public; secrets aren't workspace

Workspace content is git-backed, reviewable, shareable. Secrets, tokens, API keys do not live in workspaces — they live in ~/.hermes/profiles/<agent>/.env with strict file modes. Workspace files commit; env files don't.

Custom layerSpawn injects MC env per card

v0.15 has no native pre_spawn hook for per-card env. Bot-bound cards need MC_API_URL + MC_USERNAME at spawn from data/bots/<bot>.yaml. Resolution: small spawn layer (extension to landfolk gate-check). Bot-less cards stay on the embedded dispatcher with no change.

DisciplineRecall is episodic; marks are committed

Three storage cadences, three purposes. Recall stream = anyone-can-write-anyone-can-read sightings. Marks = committed coordinates the fleet agrees on. Workspace = audited, designed content (PR-reviewed). Don't reimplement locations-base.json inside recall; compaction may produce marks, never replace them.

DisciplineIngest vs generated — never mix

Each domain splits ingest/ (designed input, PR-reviewed) from generated/ (computed output, written only by compact: writers). Different cadences, different reviewers. A bug-fix diff shouldn't drown in nightly worksite churn.

IsolationFramework source is invisible at runtime

Workers spawn with cwd=data/workspace/. A pre_tool_call hook in the landfolk plugin enforces a path allowlist. Agents can't read bot/, plugins/, scripts/, dashboard/ — the team improves itself through workspace MRs, not by editing framework code mid-card.

SequenceTwo boards, two cadences

Operations work (real-time, per-bot mutex) and back-office work (async, worktree-isolated) live on separate boards. Don't queue script bugs behind mining tasks; don't slot mining behind doc reviews. Different metrics, different reviewers, different lanes.
