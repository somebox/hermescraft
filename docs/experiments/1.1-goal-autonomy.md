## Mechanics observations

### `/goal` behavior — confirmed and characterized

- `/goal …` works inside non-interactive `hermes chat -q …`. The chat process stays alive across many tool-call iterations.
- **The first `/goal` turn never completed in 5min 50s.** 55 tool calls + 20 interim Hermes narrative messages, all within the first agent "turn" (per the `--max-turns 90` ReAct iteration cap). The judge was never invoked.
- Per `hermes_cli/goals.py`: judge fires only when an agent turn reaches `stop_reason=end_turn`. With deepseek-v4-flash deciding "next step" repeatedly, it never stopped. The /goal turn budget (default 20) only ticks on judge calls, so it didn't tick at all.
- **Implication:** /goal's overhead (judge + continuation prompts) is amortized across full-cycle turns, but a model that doesn't naturally yield can run for many minutes inside a single turn. `--max-turns N` is the harder ceiling and worth lowering for tighter feedback loops.

### Agent reasoning quality (deepseek-v4-flash) — surprisingly good

Strategy progression observed:
1. Naive: `mc collect oak_log` from ground level — failed silently
2. Diagnostic: `mc scene`, `mc look_at`, `mc find_blocks oak_log 16` — confirmed canopy is at Y=72+, ground at Y=65
3. Strategic: "logs are way up in the canopy" → "let me try collecting dirt to pillar up"
4. Execution: collect dirt successfully, pillar from Y=65 → Y=71
5. Was about to mine canopy logs from above when terminated

The agent recognized terrain features from `scene` data, diagnosed reachability problems, and adopted a textbook Minecraft solution (dirt pillar). This is competent autonomous play, not random thrashing.

### Action-layer issues exposed

These are hermescraft, not /goal, problems — but they directly bottlenecked the task:

1. **`mc collect` silent failure mode.** Returns `ok: true` with `"Mined 0 oak_log (4 more needed). Have 0 oak_log in inventory."` in the `result` text. Top-level success masks zero-progress. **Recommendation:** add a `mined_count` integer field to the response so callers can detect failure without parsing prose. Or invert: return `ok: false` if `mined_count == 0 && requested > 0`.

2. **No `mc place` action used.** The agent successfully collected 10 dirt, but the *pillaring up* itself happened via repeated `bg_goto` to higher Y coordinates rather than a deliberate place-block action. Pillaring worked accidentally (because terrain had natural ramps), not because the bot can actively place blocks underfoot. Need to verify `mc` has a place-block primitive and surface it in skill docs.

3. **Repeatedly stuck in terrain holes** at Y=62. The bot fell into the same hole multiple times during traversal. Pathfinding doesn't seem to consider "I just got out of this hole" — needs anti-revisit memory or a body-side avoidance hint.

4. **`mc nearby` reports trees that aren't actually mineable.** Listed oak_log at Y=72 while bot was at Y=65, with no path to reach it. Either filter `nearby` to reachable blocks, or add a `reachable: bool` flag to entries.

5. **Movement spread.** Bot bounced across hundreds of blocks (354 → 406 → 359 → 401 → 395) seeking a viable tree. Suggests either trees are sparse near spawn, or the agent's exploration heuristic doesn't bias toward known good areas.

### What I would change for a successful repeat

To validate `/goal` reaches the judge step:
1. **Lower `--max-turns` to ~25** so the first agent turn ends sooner and the judge fires; verify continuation prompt arrives.
2. **Spawn the bot adjacent to a tree** (use rcon `tp Flint <x> <y> <z>` to a hand-picked oak forest biome). Removes the "find trees" subproblem.
3. **Lean observation tool.** Add an `mc observe_lean` that returns just the agent-relevant fields (position, holding, top-5 nearby items by distance). Wire the skill to prefer it.
4. **Fix `mc collect` to surface mined_count clearly.** Either field name change or status flip on zero progress.

These are out of scope for 1.1 itself (we have enough findings) but feed Phase 2 / hermescraft refactor.

### Verdict (one paragraph)

`/goal` works as a mechanism — it kept the agent reasoning autonomously for nearly six minutes without intervention, with no crashes and coherent strategy progression. But on this Minecraft task with a small worker model (deepseek-v4-flash), the **first agent turn never completed**, so the judge round never fired and we observed only the inner ReAct loop, not the full /goal lifecycle. Most of the bottleneck was the **hermescraft action layer**: `mc collect` returns `ok: true` with zero blocks mined, observation payloads are large and noisy, and pathfinding to canopy logs from ground is unreliable. The agent's reasoning quality was higher than expected — it diagnosed the canopy reachability issue and adopted a dirt-pillar strategy unprompted. To validate `/goal` end-to-end we should re-run with a lower `--max-turns`, a tree-adjacent spawn, and an observation cleanup. The bigger architectural takeaway: **`/goal` is viable as the per-character autonomy primitive, but the action layer is the throughput bottleneck and needs work in Phase 2.**

## Decisions to carry forward

1. **`/goal` is viable** as the autonomy primitive. Keep it in Phase 2 architecture.
2. **Worker model: deepseek-v4-flash works for reasoning** but its over-eager continuation defeats the judge loop. Consider `--max-turns 25` as default, or pair with a model that yields more cleanly.
3. **Judge model never tested** — verify Kimi K2.6's JSON contract works in 1.3 by giving the agent a smaller task.
4. **Hermescraft refactor needs (branch-scope):**
   - `mc collect` exit status + `mined_count` field
   - `mc observe_lean` for tool-response trimming
   - `mc place_block` primitive (check if exists; surface in skill if so)
   - Reachability filter in `mc nearby` outputs
   - Anti-loop memory for `mc goto` (skip recently-failed waypoints)
5. **Phase 2 architecture implications:**
   - Each character's `/goal` mission needs a starting position (mark or `mc tp_self`) so it's not relying on biome luck.
   - The orchestrator's success-predicate tooling should NOT just check `ok:true` — must inspect domain fields (`mined_count`, inventory diff).
