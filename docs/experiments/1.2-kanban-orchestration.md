## Architecture as observed

Hermes Kanban is **richer than the videos suggested** — it's not "Kanban as cron pattern," it's a full distributed task queue:

### Storage / state
- SQLite DB at `~/.hermes/kanban.db` is the source of truth. Atomic claims (lock = hostname:pid+expires).
- Each task has its own workspace dir.
- Each task has its own log file with the full Hermes session output.

### Lifecycle
```
triage  →[specify]→  todo  →[deps met]→  ready  →[claim]→  running  →  done | blocked | failed
```
- **`triage`**: human posts a coarse one-liner; specifier flesh-out is pending.
- **`todo`**: spec'd but waiting (either no assignee, or has unmet parent dependencies).
- **`ready`**: claimable by the assigned profile.
- **`running`**: a worker process holds the claim.
- **`done`**: completed; result + summary persisted.
- **`blocked`**: explicit block (manual or auto after N failures).

### Workers
- One **process per claim**: `hermes -p <profile> --skills kanban-worker [--skills <extra>] chat -q "work kanban task <id>"`.
- **Profiles can run multiple tasks concurrently** — each is a separate hermes process with its own session. **No mutex on profile.**
- Worker auto-loads `kanban-worker` skill plus any per-task `--skill` flags.

### Dispatcher
- Embedded in `hermes gateway` (long-running daemon, launchd-managed on macOS).
- Tick interval default 60s.
- Per tick: scan ready tasks, atomically claim one per assignee, spawn worker process, update statuses for completed runs.
- Dependency resolution: a task with unmet parents stays in `todo` (not `ready`), so dispatcher skips it.
- Reclaim: stale claims (worker crashed, lock expired) get reclaimed and re-dispatched on next tick.
- Auto-block: after `failure_limit` consecutive non-success attempts, task → `blocked`.

### CLI surface (highlights)
```
hermes kanban init                               # create kanban.db
hermes kanban boards                             # multi-board support
hermes kanban create [--triage] [--assignee X] [--skill S] [--max-runtime 30m] TITLE
hermes kanban specify <id> | --all               # promote triage → ready (LLM call)
hermes kanban list                               # all tasks (status icon prefixed)
hermes kanban list --status <status> --json      # filter / structured
hermes kanban show <id>                          # full task with comments/events/runs
hermes kanban link <parent> <child>              # add dependency
hermes kanban assign <id> <profile>
hermes kanban reassign <id> <profile>
hermes kanban dispatch [--dry-run]               # one-shot dispatcher pass
hermes kanban daemon                             # DEPRECATED — use gateway
hermes kanban tail / watch / runs / log <id>     # observability
hermes kanban diagnostics                        # active diagnostics
```

### Agent-side tools
The kanban-worker skill auto-injects a system prompt block; tools available include:
- `kanban_show`, `kanban_create`, `kanban_link`, `kanban_complete`, `kanban_block`, `kanban_comment`, `kanban_heartbeat`.

So workers can:
- Read their own task and any others.
- Spawn child tasks (fan-out) — confirmed below.
- Comment for status updates (heartbeats).
- Mark themselves complete or blocked.

## Variants run

### Variant A — single coarse card → specifier promotes to ready ✅

**Setup:** `hermes kanban create --triage "Compare three open-source LLM agent frameworks…"` → `hermes kanban specify <id>`.

**Result:** specifier (a one-shot LLM call against the *active* profile, here `default` = gemini-flash-latest) took the one-liner and produced:
- Retitled task: "Compare three open-source LLM agent frameworks in a one-page report"
- Structured body with **Goal**, **Approach**, **Acceptance criteria**, **Out of scope** sections.
- Status moved triage → ready (skipping `todo` when no deps).
- Recorded an audit comment: "Specified — updated title, body and promoted to todo."

**Time/cost:** sub-second LLM call. Free-ish on cheap models.

**Insight:** the specifier is a **single LLM call**, not a cron-driven librarian profile that polls. The video's "librarian on a cron checks triage every 10 minutes" pattern is one *workflow* on top — the lower-level primitive is the imperative `kanban specify` command.

### Variant B — multi-card pipeline with dependencies ✅ (in progress at write time)

**Setup:** 4 cards with explicit dependencies:
- `t_ac1841ed` (R1, worker-a, +research-paper-writing skill) — list 3 open-source LLM-driven game-AI projects
- `t_1f258489` (R2, worker-b, +research-paper-writing skill) — list 3 academic papers on LLM agents in simulated worlds
- `t_6b1a93e4` (A, worker-a) — depends on R1+R2 — synthesize feature comparison
- `t_399b3aa5` (W, worker-b) — depends on A — write-up paragraph

Linked via `hermes kanban link` (parent → child). Dispatched via `hermes kanban dispatch`.

**Observed:**
- R1 + R2 immediately spawned in parallel (one process per profile per task).
- A and W stayed in `todo` while parents were unfinished.
- **R2 (worker-b) completed in 94 seconds** — produced a real markdown file `papers.md` (1718 bytes) with 3 plausible academic papers in proper bibliography format. Worker auto-wrote a summary string back to the task.
- R1 (worker-a) ran a more elaborate strategy: used `delegate_task` to spawn **3 parallel research subagents** (CrewAI, LangGraph, AutoGPT), then continued with terminal-based GitHub stat lookups. Total: ~50s for the delegation block, more for follow-up.
- t_f5ed9212 (variant A) ran on worker-a in parallel with R1. **Confirmed: the same profile can hold multiple concurrent claims** with separate processes/sessions.

**Critical finding:** workers use `delegate_task` for fan-out *within* a single Kanban task. So the architecture has two parallelism layers:
1. **Kanban level**: many workers across many profiles, claimed atomically.
2. **Agent level**: a single worker can fan out internally via `delegate_task` (max 3 children, blocking parent).

This explains the kanban-orchestrator skill's "use delegate_task for short fan-out, kanban for long-lived multi-specialist work" framing.

## Observations

### What the librarian / specifier actually does (per `kanban specify`)
- Takes the title (and any partial body).
- Calls the active profile's LLM with a system prompt that asks for: improved title, structured body (Goal/Approach/Acceptance/Out-of-scope), and an action.
- Updates the task in DB; records an audit comment.
- Promotes triage → todo or ready depending on whether parents exist.
- **Does not assign workers** — that's a separate `hermes kanban assign` step (or `--assignee` at create time).
- **One-shot, not cron** at this level. Cron-based "librarian" pattern from the videos is a workflow built on top.

### Workers handling complex tasks
Worker for `t_f5ed9212` (the original variant-A coarse card, deepseek-v4-flash):
1. Auto-called `kanban_show` to read its task.
2. Made a 5-step internal plan (visible via `📋 plan 5 task(s)` in log).
3. Used `delegate_task` to spawn 3 parallel research subagents.
4. Followed up with terminal commands for GitHub stat lookups.
5. (still running at write time)

### Dispatcher behavior with the gateway
- Started gateway via `hermes gateway start` — registered launchd service `ai.hermes.gateway`.
- Gateway logs: cron ticker (60s), kanban dispatcher embedded (60s). Both run from the same process.
- Once running, completed parents auto-promote children to ready on the next tick (≤60s lag).

### Cost/scale notes
- Worker profile model choice matters a lot — research-paper-writing on deepseek-v4-flash worked well (~94s for one task).
- Dispatcher spawning a hermes process per claim is *heavy* (Python startup ~500ms, skill loading more). Don't aim for sub-second tasks; tasks are minute-scale work units.
- Concurrency of N profiles × M concurrent claims: confirmed feasible. Memory grows ~100MB per active worker.

### Surprises
- **No mutex on profile**: I expected one-task-per-profile, observed otherwise. Means a Hermes profile is more like a "config persona" than a "worker slot."
- **Dispatcher is launchd-installed by default** (macOS). `hermes gateway start` registers a plist that auto-starts on login. Need to remember `hermes gateway stop` + remove plist when done.
- **Specifier uses the active profile**, not a pre-configured "librarian." Means: to use a specific model for specification, you `hermes profile use librarian` first, then `hermes kanban specify`.
- **The kanban-orchestrator skill never actually fired in this run** — there's no profile assigned to it. The "decomposition playbook" lives in the skill, ready to inject into any worker that's given the orchestrator role. Not exercised yet.

## Findings to carry into 1.3 and Phase 2

1. **Kanban as the multi-agent substrate is solid.** Atomic claims, dependency resolution, per-task workspaces, audit log, autoreclaim — all there. Use this for hermescraft multi-bot coordination.
2. **For Minecraft bots, "the worker process is a Hermes session" maps cleanly.** The bot brain is already a Hermes session today; replacing the round-loop launcher with a kanban-claimed worker is a small wrapper change.
3. **Dispatch model needs adjustment for long-lived bot work.** The current dispatcher spawns one process per claim and expects the worker to mark `complete`. A Minecraft bot's "task" might be "play your goal-preset until reassigned." Either:
   - Each goal becomes a kanban task that ends when its success predicate fires (bot calls `kanban_complete`).
   - Or, the bot is a daemon and the kanban tracks discrete missions that the daemon polls and executes.
   The first matches the kanban architecture better; the second is closer to current hermescraft.
4. **Specifier as the steward's mind.** The pattern of "human posts coarse intent → LLM enriches into a structured spec" is exactly what the steward in our target architecture should do for Minecraft missions. We can reuse the specifier mechanism wholesale — set a profile to a steward model, run `kanban specify` on triage cards.
5. **Workers can fan out via `delegate_task`** while doing a kanban task. Useful for one-off concurrent subtasks within a worker (like spawning research lookups). NOT useful for long-lived child tasks (that's what kanban dependencies are for).
6. **Dashboard inspection works.** The Kanban UI in the dashboard SPA gives a non-CLI way to monitor — useful for the user during experimentation. (User to verify visually.)
7. **Skill `--skill <name>` per task** is a clean way to scope tools and prompt context. We can have `--skill minecraft-flint-mission` per Flint task, `--skill minecraft-mason-mission` per Mason task. Combined with `--workspace dir:~/hermescraft/data/marks/...`, each task has the exact context it needs.

## Decisions / open issues

- **Open:** does Variant C (mid-task reassignment) work cleanly? Worth verifying before depending on it for "steward nudge" semantics.
- **Open:** what is the runtime of `dashboard` for the kanban view specifically? User-test required.
- **Open:** do we need a `--max-runtime` per Minecraft task? Probably yes (e.g. "achieve X within 20 minutes or hand back").
- **Decision:** in Phase 2 architecture, **kanban becomes the steward's primary control surface**. The steward edits goal-presets *via* kanban tasks, rather than writing files directly. This gives audit trail + ability to inspect via dashboard.
