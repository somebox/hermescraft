# Experiment 1.3 — Two-Agent Collaboration (and the goal-preset reactivity question)

**Status:** complete (with critical architectural finding)
**Run window:** 2026-05-09 14:08 → 14:13 (~5 minutes wallclock)

## Question (revised)

The plan called for "two bots collaborate on a 5x5 cobble shelter." Given the action-layer issues found in 1.1, I narrowed the test to the **architecturally critical question**: *can an external orchestrator drive a long-running `/goal` session by writing entries into the bot's goal-engine?*

If yes → the steward-edits-goal-presets pattern from our preliminary architecture works.
If no → we need a different control surface (chat / kanban / file-watching / extended goal-engine).

## Setup

- Two Mineflayer bot bodies: Flint on port 3001, Mason on port 3002, both connected to `192.168.1.202:25565`.
- Two `/goal` sessions, one per bot, deepseek-v4-flash, `--max-turns 30`, with new skill `minecraft-preset-reactive` instructing the agent to read `mc goals` each cycle and pursue the top-urgency entry.
- Scripted orchestrator at `~/hermescraft/scripts/orchestrator-v0.sh`:
  1. POST `/goals` to inject a new goal `exp_collect_dirt` (metric `dirt_total`, target_min=2, priority=250).
  2. Poll `/inventory` every 10s checking `dirt` count.
  3. When threshold hit, switch to Mason and repeat.
- Both bots cleared via rcon `clear` before start (Mason had **294 items** removed — substantial state from earlier sessions; flint's prior 10 dirt also cleared).

## Critical finding 1: custom goal-engine entries with unrecognized metrics get urgency=0

When the orchestrator injected `exp_collect_dirt` with `metric: "dirt_total"`, the bot's `/goals` endpoint accepted the entry and returned it in the list — but with `urgency: 0.1, gap: null`.

`mc goals` (which is what the agent reads) sorts by urgency, **not priority**. Priority=250 was meaningless. The agent saw `maintain_food` (urgency 1.38) at the top of its list and chased food/animals.

**Why:** the goal engine has a fixed set of registered metric evaluators (`food_score`, `pickaxe_durability_pct`, `iron_total`, `coal_total`, `stone_total`, `diamond_total`, `chest_mark_total`, `threat_score`, `survive_score`). An unknown metric like `dirt_total` cannot be evaluated → `gap` is null → urgency stays at the priority-derived floor (~0.1). This is in `bot/lib/goals/engine.js`.

**Implication for Phase 2 architecture:**
> "The steward writes goal-preset entries to drive bots" — this works **only for retargeting metrics the engine already knows about**. For arbitrary new objectives we need a different control surface.

## Critical finding 2: retargeting an existing recognized metric DOES work

Follow-up test: instead of injecting a new goal, I `POST /goals/update` with `id: supply_cobblestone, target_min: 2, priority: 250`. Result:

```
supply_cobblestone   pri=250  urgency=1.5  gap=4  target_min=2     ← top
maintain_food        pri= 90  urgency=1.38 gap=60                  ← was top
maintain_pickaxe     pri= 85  urgency=1.15 gap=60
...
```

`supply_cobblestone` jumped from urgency 0.9 (with target 64) to urgency 1.5 (with target 2), and is now top-ranked. **Retargeting works.**

**Implication:** the steward CAN drive bots by adjusting the *targets* of existing metrics. To say "Flint, focus on stone now" → set `supply_cobblestone target_min` low. To say "deprioritize food" → raise its target_ok. Within the existing metric vocabulary, the steward has full priority control.

## Critical finding 3: `/goal` sessions are short-lived in practice

Both `/goal` sessions exited within ~5 minutes of start (max-turns 30 hit, possibly judge-driven exit too — wasn't conclusive). This **conflicts with my preliminary architecture's assumption** that each character would have a continuously-running `/goal` brain in tmux.

In observed behavior:
- Deepseek-v4-flash on `--max-turns 30` ran ~25-30 tool calls inside one agent turn before yielding, then the next turn happened, then somewhere between turn 1 and turn 5 the session ended.
- The agent did call `mc goals` and noticed urgency changes ("Let me re-check goals since the urgency ranking shifted") — but the session ended before reacting to the new top goal.

**Implication for Phase 2 architecture:**
- Pattern A — long-lived /goal in tmux, bot brain reads goals on each cycle: NOT VIABLE without an auto-restart wrapper (which is what hermescraft.sh already does).
- Pattern B — kanban-driven per-mission spawn, dispatcher creates a fresh `/goal` worker per mission: maps cleanly onto what we observed in 1.2. **This is a much better fit.**

## Critical finding 4: `mc collect` confirmed broken; `mc dig` works

In 1.1 we suspected `mc collect` had silent failures. In 1.3 the agent independently discovered this and switched to `mc dig <x> <y> <z>`:

```
$ mc collect oak_log 4   → 0 mined despite ok:true (silent failure)
$ mc dig 399 73 -638     → succeeded; 1 oak_log added to inventory
```

**Implication:** confirmed branch-scope refactor needed. The `mc collect` action either has a real bug, or its semantics differ from what skills claim. Either way, the agent can't trust the result.

## Critical finding 5: agents diverge from skill instructions

Despite the explicit `minecraft-preset-reactive` skill telling the agent to read `mc goals` each cycle and execute the top entry, both agents pursued goals NOT at the top of the urgency-ranked list:

- Flint went after oak logs (memory from 1.1) instead of food/pickaxe (urgency-top).
- Mason chased apples for "food score" reasons that didn't match urgency calculation.

**Reasons (probable):**
- Memory contamination — Flint's session memory still had hooks from the 1.1 canopy-log narrative.
- Skill instructions are advisory; the agent's broader judgment can override them.
- The "preset-reactive" skill conflicted with the deeper "minecraft-goals" skill which has its own decision logic.

**Implication:** for the steward pattern to work, we need a **stricter contract** between the agent and the goal engine — possibly:
- A per-character instruction that *overrides* skill conflicts.
- A workspace-scoped agent (no cross-session memory).
- Or: instead of telling the agent "read goals each cycle," wrap each mission in its own `/goal` invocation with a goal text that names the specific objective ("mine 8 cobble"). Pattern B from finding 3.

## Pipeline outcome

The orchestrator timed out at phase 1 (~101s) without Flint hitting the 2-dirt target. Flint instead mined 2 oak_log via `mc dig` — proving the agent can mine but pursued the wrong objective. Phase 2 (Mason) was never reached.

**Net architectural learning:** the experiment "failed" at the original goal but **succeeded as an investigation** — we now know exactly which architectural assumptions to discard and which to keep.

## Decisions for Phase 2 (revised architecture)

The preliminary architecture sketched in the plan needs **major revisions**:

### Was (preliminary): per-character long-lived `/goal` + steward edits goal-presets
### Now (revised): kanban-driven mission spawns + steward-as-task-creator

1. **Bot brain ≠ long-lived process.** A "bot brain" is a *family* of short-lived `/goal` sessions, each spawned by the kanban dispatcher to execute one mission against the bot's HTTP body.
2. **Steward profile is a kanban-orchestrator role.** Steward reads world state (in-game observation + bot inventories), creates kanban tasks, assigns them to character-named profiles (`flint`, `mason`, `gatherer`, `barley`).
3. **Each character is a Hermes profile** that serves as the assignee for kanban tasks. The dispatcher spawns a `hermes -p flint --skills kanban-worker,minecraft-flint-mission chat -q "work kanban task <id>"` process per mission.
4. **Workers use `/goal` internally** to drive their single mission to completion. Mission ends → process exits → kanban marks done → next mission spawned by dispatcher.
5. **Goal-preset retargeting is still useful** for *micro-adjustments* mid-mission (e.g., "low food! eat first"), but not for cross-mission coordination — that's what kanban is for.
6. **Steward in-game presence still works** — can be a specific Hermes profile with its own bot body, doing its in-game ATC duties as one of its kanban-driven missions ("patrol tower for 10 min").

This is *much* simpler than the preliminary architecture and matches what Hermes actually does well.

## Branch refactors recommended (Phase 1 → Phase 2 carry-over)

These were already partially identified in 1.1 but are now urgent:

- [ ] **Fix `mc collect` or surface its failure clearly.** Silent zero-mined returns broke automation in 1.1 and 1.3. Either return `ok:false` when `mined_count==0` while `requested>0`, or expose `mined_count` as a top-level field.
- [ ] **Custom metric registration in goal engine.** `bot/lib/goals/engine.js` should accept arbitrary `metric` names and treat unknown metrics as "always 0 / target unmet" rather than ignoring. (Or expose an `evaluate_fn: <expr>` field per goal.)
- [ ] **Lean observation tool.** Confirmed in 1.1: tool responses are 90% of message bytes. `mc observe_lean` would help substantially.
- [ ] **Bot HTTP API contract docs.** I had to grep `http-app.js` to find the route table. A `/api-spec` endpoint that returns the OpenAPI of available routes would speed integration work.
- [ ] **Mission-scoped session memory.** Per finding 5, agents leak narrative across runs. A `--ignore-rules --workspace dir:<task_workspace>` invocation pattern (already supported by `hermes chat`) might help.
