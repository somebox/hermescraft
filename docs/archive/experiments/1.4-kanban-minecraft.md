# Experiment 1.4 — Kanban-driven Minecraft Work (dig + fill)

**Status:** complete (success — both phases finished cleanly)
**Run window:** 2026-05-09 17:24 → 17:32 (~8 minutes wallclock end-to-end)

## Question

Can two character profiles cooperate on a Minecraft task driven entirely by the Hermes Kanban system — with the kanban dispatcher spawning workers, dependencies cascading, and comments serving as inter-card IPC? This is the validation of the **revised Phase 2 architecture** sketched in the Phase 1 summary.

- **Profiles:** `flint` (deepseek-v4-flash, env `MC_API_URL=http://localhost:3001`, `MC_USERNAME=Flint`), `mason` (same model, port 3002, `Mason`). Both with `terminal.env_passthrough: [MC_API_URL, MC_USERNAME]`.
- **Bot bodies:** Flint on 3001 → Paper 1.21.4, Mason on 3002, both at world coords near (400, 64, -600).
- **World prep (rcon):** `fill 400 64 -600 400 68 -600 minecraft:dirt` (5-block dirt column), `give Mason cobblestone 8`, `clear Flint`, `tp` both bots adjacent to the column.
- **Cards:**
  - **A** (`t_577617be`, assignee `flint`, no parents): "Dig 4 dirt blocks at the column (400, 65/66/67/68, -600). Use `mc dig X Y Z`, NOT `mc collect` (known bug). Post a kanban_comment when done; end with kanban_complete."
  - **B** (`t_70e98702`, assignee `mason`, parent `A`): "Read parent A's comments via `kanban_show`. Use `mc place cobblestone X Y Z` to fill (400, 65/66/67/68, -600). You start with 8 cobblestone."

## Two pre-flight bugs surfaced and fixed on the branch

### Bug 1: `mc` shell wrapper broke when invoked via symlink
`/Users/foz/.local/bin/mc` is a symlink → `~/hermescraft/bin/mc`. The script used `BASH_SOURCE[0]` without resolving symlinks, so `$DIR/../bot/cli/index.mjs` looked under `/Users/foz/.local/bot/...` (doesn't exist). Workers spawned without `PATH` overrides hit this immediately on first `mc status`.

**Fix:** added a `readlink` loop to resolve symlinks before computing `DIR`. Committed in `bin/mc` on `experiment/hermes-agents`.

### Bug 2: per-profile env didn't reach the terminal subprocess
Even with `MC_API_URL=http://localhost:3001` in `~/.hermes/profiles/flint/.env`, the agent's terminal subprocess didn't inherit it because Hermes' default `terminal.env_passthrough` is `[]`. Result: `mc` couldn't reach the bot's HTTP server.

**Fix:** edited each profile's `config.yaml` to set `terminal.env_passthrough: [MC_API_URL, MC_USERNAME]`. After this, `mc status` worked first try.

After both fixes, the experiment ran cleanly. Reclaimed Flint's stuck task with `hermes kanban reclaim t_577617be`; the dispatcher spawned a fresh worker on the next tick.

## Findings — answered the user's questions

### "How much access can agents have to cards?"

Confirmed via source + behavior:

- **`kanban_show <id>`** — full read access to ANY card: title, body, status, comments thread, last 50 events, run history, parents, children, workspace_path. Plus a pre-built `worker_context` string that the dispatcher generates at spawn time (which includes parent comments by default — Mason got Flint's comments injected into its system prompt without explicitly fetching).
- **`kanban_comment <id> body`** — write a comment to any card. Author is auto-set from `HERMES_PROFILE` env (cannot be forged). Cross-task commenting allowed.
- **`kanban_create`** — spawn child cards with title, assignee, body, parents, skills, max_runtime, workspace_kind.
- **`kanban_link`** — add deps post-hoc (cycles rejected).
- **`kanban_complete`** — declare done with summary, result, metadata, and `created_cards` list (hallucinated card IDs are rejected).
- **`kanban_block`** — block with reason.
- **`kanban_heartbeat`** — extend claim TTL.
- **No attachment field.** Files live in workspace dirs (`workspace_path` on the card); the kanban-worker is auto-spawned with `cwd=<workspace_path>`. Workers find sibling outputs via `find` + `read_file` — confirmed working in 1.2's analysis worker reading sibling `papers.md`.

### "Can dependencies coordinate work and goals?"

**Yes — confirmed clean cascade.** Phase B was created with `--parent t_577617be`, sat in `todo` while A was running, and auto-promoted to `ready → running` on the dispatcher's next tick after A's `kanban_complete`. Latency: ~10s from A's done to B's claim.

The dispatcher correctly:
- Held B in `todo` until A was `done`.
- Fed Mason's worker a `worker_context` system prompt block that **already contained Flint's `kanban_complete` summary AND comments**, so Mason didn't have to call `kanban_show t_577617be` explicitly — the orchestration pre-loaded the relevant context.

### Comments-as-IPC works at the architecture level

Mason's behavior shows the pattern: the dispatcher injects parent comments into the next worker's system prompt; the worker reads them as part of its initial briefing; the worker then comments on its own card to close the loop.

Total IPC volume in this run:
- Flint's comment: 358 chars
- Mason's comment: 621 chars
- Both summaries (auto-fed to next worker): ~250 chars each

**Token cost of comments-as-IPC is negligible** at this scale. Even with 4 characters and 20 missions/day, comments + summaries would be under 50KB/day of LLM input — trivial.

## Architectural validation: revised Phase 2 model works

The Phase 1 summary proposed:
> kanban-spawn-per-mission + steward as orchestrator profile + characters as kanban assignees + comments as IPC

This experiment **validates that model end-to-end**:
- ✅ Per-character profiles with per-bot `MC_API_URL` envs work (after env_passthrough fix)
- ✅ Dispatcher spawns one hermes process per claimed task, properly threaded with profile env
- ✅ Card body is the mission contract (clear, mission-scoped)
- ✅ `mc dig` works reliably (vs broken `mc collect` from 1.1/1.3)
- ✅ Workers self-correct when actions fail (Mason's foundation insight, Flint's grass_block discovery)
- ✅ Dependencies coordinate gameplay sequentially without polling

This is the architecture Phase 2 should formalize.

## Surprises and small lessons

1. **`worker_context` is a hidden killer feature.** The dispatcher pre-builds a context block that includes parent comments + summaries and injects it into the worker's system prompt. We didn't have to write any "read parent" wiring — it just worked. Phase 2 plan should call this out.
2. **Workers reason about Minecraft physics autonomously.** Mason recognized "no solid neighbor" and built a foundation. Flint recognized grass_block drops dirt. These weren't in any skill or briefing.
3. **Reclaim works.** When the first Flint worker hung on the broken `mc` symlink, `hermes kanban reclaim` released the claim cleanly and the dispatcher spawned a fresh worker on the next tick.
4. **Tool errors propagate as agent-readable text.** `mc dig 400 65 -600  0.3s [error]` — the agent saw the failure and adapted. Combined with `mc find_blocks` for re-orientation, this is a robust loop pattern.
5. **bot_position differs from agent assumption.** Flint at (401.5, 64, -599.5) was inside the column (column is at x=400) — bot's body and feet straddle multiple X coords because of float position. Agents must be careful about which coords they target. A `mc dig_facing` or `mc dig_relative` helper might be ergonomic.
6. **Mason did off-spec work and succeeded.** The card said place at Y=65-68; Mason placed at Y=64-68 (5 blocks instead of 4) to give the pit a base. The card success was still met because Y=65-68 are all cobblestone now. **This is a real architectural concern for missions with strict block-by-block specifications** — workers may "improve" the brief.

## Cost / scale notes

- Total LLM time across both workers: ~5 minutes.
- Estimated cost on deepseek-v4-flash: well under $0.10.
- Per-worker spawn overhead (Python startup + Hermes init + skill loading): ~5–8s before first tool call. **Significant** for sub-minute missions; negligible for missions of 30s+.
- For 4 characters × 20 missions/day, this implies ~50 minutes of worker-time/day at this complexity. Very manageable.

## Branch refactors carried over

Already on the branch as part of this experiment:
- `bin/mc` symlink resolution fix
- New profile config patterns (env_passthrough for MC_API_URL/MC_USERNAME)

Still recommended (from 1.1, 1.3, reaffirmed here):
- Fix or replace `mc collect` (silent zero-mined failures)
- `mc observe_lean` (token diet)
- Custom metric registration in goal engine
- Anti-revisit memory in pathfinder
- `/api-spec` endpoint on bot HTTP server

New ideas surfaced by 1.4:
- **`mc dig_facing` / `mc place_facing`** — placement relative to bot's facing direction, avoiding "no solid neighbor" errors when the bot can clearly reach the target.
- **`kanban_workspace(parent_id)` tool** — explicit helper that returns the parent task's workspace path, so workers don't need to `find` their way around.
- **Card spec strictness levels** — tag cards as `strict` or `permissive` so workers know when they can deviate (e.g., Mason's foundation insight) vs. when they must match exactly.

## Decisions for Phase 2

1. **Adopt kanban-driven mission spawn as the core architecture.** Validated end-to-end here.
2. **Per-character Hermes profile** with `MC_API_URL` and `MC_USERNAME` in profile `.env`, plus `terminal.env_passthrough` for those vars in `config.yaml`. Codify in a `bootstrap` script.
3. **Steward profile** is a distinct kanban assignee that holds tasks like "decompose this mission" — same machinery as workers.
4. **Comments-as-IPC** is the canonical handoff channel; design Phase 2 task templates to use them deliberately.
5. **`worker_context` injection** is the bridge between cards — Phase 2 should NOT try to replace it.
6. **`/goal` is one tool a worker can use** for sub-step planning *within* a single kanban task, but not the orchestration primitive. Confirmed by 1.4's success without `/goal` at all.
