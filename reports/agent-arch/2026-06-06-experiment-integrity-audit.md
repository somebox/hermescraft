# Experiment integrity audit — pinch test and chain comparison

> **Follow-up:** a [clean comparison report](./2026-06-06-clean-comparison.md) re-ran × 3 each side with full reset between every run. Turn-1 context is now reproducible within 2 tokens, and the headline reversed: narrow wins on the metrics the architecture cares about. The reset addresses 9 of the 12 contamination sources listed here.

**Date:** 2026-06-06 late evening, after the [pinch test](./2026-06-06-live-pinch-test.md), the [replication](./2026-06-06-pinch-test-replication.md), and the [multi-phase chain](./2026-06-06-multi-phase-chain-comparison.md).

A reviewer asked whether the agent profiles had leftover state and whether the test conditions actually exercised what the reports claim. They mostly did not. This audit lays out what was contaminated, what was fair, and what the comparisons can and can't still tell us.

## How this affects each comparison

### × 3 replication on single-phase nav (`2026-06-06-pinch-test-replication.md`)

**Claim under audit:** wide beats narrow on every metric except success rate.

**Contamination:**
- Both sides accumulated MEMORY.md entries across runs. By narrow3, the navigator had narrow1 and narrow2's exit positions cached. Same for wide3.
- This biases *both* sides toward improvement over time. Not fatal — the mean comparison is still apples-to-apples if accumulation rates are similar.
- The turn-1 context measurements (49,727 narrow, 38,833 wide) include MEMORY.md size. Narrow's memory had 7 entries by chain time; flint's had 4. ~1 k token difference at most.

**What still holds:**
- Wide *was* more token-efficient on the completed task.
- Wide *was* faster wall time.
- Both sides 3/3 success rate.

**What needs an asterisk:**
- The "turn-1 in-context" comparison conflates two things: catalog noise (flint has 105 skills' descriptions injected; pilot has 4) and eager skill preload (pilot's kanban-worker SOUL preloads agent-navigator.md body via skill_view turn 1; flint's lazy-loads). The original report's headline that "wide's turn-1 is smaller" is true in token count but is the SUM of these opposing effects — bigger catalog vs eager preload.
- A fair test would either:
  - Strip flint to only its mc-relevant skills (or load skill descriptions lazily), OR
  - Configure pilot's SOUL to lazy-load like flint does
- We didn't do either.

### Multi-phase chain vs one-card flint (`2026-06-06-multi-phase-chain-comparison.md`)

**Claim under audit:** chain completes, wide one-card blocks before doing real work.

**Contamination — test invalidating:**

The flint card body says: *"Complete when you have at least 4 oak_log in inventory AND are within 2 blocks of :island_start:"*. At the moment the flint card was created:

- The bot was at (-28.6, 64, -27.4), within 2 blocks of `:island_start:` (-29, 64, -28) ✓
- The bot's inventory contained 4 oak_log because **I had tossed 4 oak_log to clear inventory before the run, and the bot auto-picked-them-up** while standing on top of them ✓

Flint's worker called `mc status`, `mc read_chat`, `mc marks`, and noted in its MEMORY: *"task conditions already met"*. It was correct. The card was not a "failure to do mining" — the predicate was already true at turn 0. The auto-stuck-check then fired because `mc status` / `mc marks` / `mc read_chat` don't change world state, so the `recent[]` fingerprint stayed constant.

**This invalidates the chain-vs-one-card comparison.** The chain side did real mining work (61 calls, scope-drifted into crafting); the flint side correctly identified no work was needed and tried to early-exit. The token / wall-time / "chain succeeded vs wide failed" framing in the report is misleading.

**Other contamination:**
- The chain miner crafted a wooden_axe + oak_planks during card 2. The wooden_axe was useful for subsequent log-mining. This may have led to the runaway 41-call sequence (worker saw an opportunity, took it, then had to "do mining" with the new tool).
- The chain navigator card 1 had the bot die once in water: *"got stuck in water and died once, respawned at (16,69,-80), then walked to mine_entrance"* per MEMORY. The 96 s card time hides this — a real comparison would need to control for unplanned deaths.
- The flint one-card body was about 12× longer than the chain card bodies (one sentence vs three numbered steps + completion predicate). More prose to reason about on turn 1.

### Original pinch test (`2026-06-06-live-pinch-test.md`)

Already known to be unreplicable (the replication report supersedes it). The audit adds: the original wide failure included flint's MEMORY.md being empty for pinch_target at that point, so the wide worker had no prior nav-to-mark experience. By contrast, the narrow worker started fresh too. So that ONE comparison was actually less contaminated than the replication's later runs.

## What was actually fair across the experiments

These pieces were consistent and not load-bearing for any of the audit findings:

- **Model:** `deepseek/deepseek-v4-flash` via OpenRouter, both sides, every run.
- **Bot:** Same flint Mineflayer process on port 3002. Same in-game body.
- **Marks via bot HTTP:** server-side; both narrow and wide queried `mc marks` and got the same list. Auto-marks created mid-test (crafting tables, death points) appeared for all subsequent runs equally.
- **Hermes version:** v0.16.0 throughout.
- **Toolsets in config:** both `hermes-cli` (so terminal, kanban, memory, session_search, etc. all available to both).
- **Same start position** at each run start, reset via direct bot HTTP `mc move` calls (no LLM cost).

## What the audit changes about the conclusions

1. **The chain vs one-card comparison is invalid.** The flint card's completion predicate was already true at start. The report headline should not be cited as evidence for the chain pattern.

2. **The single-phase replication is mostly valid but needs caveats.** Both sides had cumulative MEMORY effects; both got smarter over their × 3 runs. The "turn-1 context" gap (49.7 k narrow vs 38.8 k wide) is the wrong measurement to draw conclusions from — it's a sum of catalog noise (favoring narrow) and eager preload (favoring wide), and we can't separate them from the existing data.

3. **The architecture's bet hasn't actually been tested cleanly.** The right next test:
   - Build a narrow profile with no MEMORY.md history, no preload (SOUL says "lazy load skills as needed"), and the same SOUL length as flint's.
   - Build a wide profile with only mc-relevant skills installed (no apple-notes, no claude-design).
   - Run both on a task neither has seen before, where the completion predicate cannot be pre-satisfied by inventory or position.
   - Run × 5+ each side to get variance.

4. **The narrow architecture's real architectural lever might be `.skills_prompt_snapshot.json` size, not skill bundle narrowness.** A 60 kB skill catalog injected as turn-1 context noise is a measurable cost; the apparent narrow vs wide differences in the existing data are mostly explained by this.

5. **MEMORY.md is doing more architectural work than the prototype design accounted for.** Each completed card auto-writes a summary the next session reads. The narrow workers got "smarter" about marks they'd visited; the wide workers same. This is a real feature of Hermes profiles, not unique to either side, but it means the "fresh worker per card" framing from `target.md` was incomplete — the worker is fresh but the **profile** carries learning across cards.
